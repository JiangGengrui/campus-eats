校园外卖平台

01全局拓扑

三包一库。依赖方向单向，shared 是两端唯一的共同语言。

client:5173
React SPA，浏览器里的全部界面与交互
  • react-router-dom 路由与守卫
  • zustand：auth / cart 两个 store
  • axios 单例访问 /api
⇄HTTP
/api
server:3000
Express API，鉴权、校验、事务、SQL 全在这一侧
  • 5 个业务域，每域四件套
  • JWT 鉴权，不留服务端会话
  • better-sqlite3 同步驱动
⇄SQL
参数化
SQLite*.db
单文件数据库，WAL 模式，外键开启
  • 9 张表 + 6 个索引
  • 金额一律 INTEGER 分
  • 软删除，不物理删行
shared · 两端共享 types.tsschemas.tsorder-status.tserror-codes.ts 源码直接消费，改完必须全仓 typecheck
  • 规则依赖单向：client → shared ← server。client 永不 import server，server 永不 import client。
  • 规则shared 只放三类内容：DTO 类型、业务规则（状态机、错误码）、zod 校验 schema，不写 DB 访问与运行时业务。
  • 规则金额不分叉：库、接口、内存一律 INTEGER 分，只有展示层 ÷100。
  • 结果任一端改字段，另一端的类型错误会在 tsc 阶段暴露，而不是在运行时。

03一次请求的链路

以「结算页点击模拟支付」为例。点击左侧任一层，查看它的职责、禁止事项与代码形态。

统一约定两端都靠它说话

响应壳

{
  "code": 0,
  "message": "ok",
  "data": { "id": 12, "orderNo": "20261108004217" }
}

客户端只认 code === 0 为成功，其余按业务错误处理。

错误链路

  • service 抛 new AppError(code, message, httpStatus)
  • 全局 errorHandler 转成响应壳与 HTTP 状态码
  • 错误码集中来自 shared/error-codes.ts，禁止裸数字
  • controller 里禁止 try/catch 吞错

中间件顺序固定，不可调换

helmet → cors（仅放行 5173）→ express.json({ limit: '1mb' }) → morgan → /uploads 静态 →
路由（requireAuth / requireAdmin）→ notFoundHandler → errorHandler

04服务端四件套

每个业务域固定 4 个文件，职责不交叉。这一条决定了项目「能不能讲清楚」。

层文件只做这些禁止
路由<域>.routes.ts挂载路径、套中间件、zod 校验入参业务逻辑、直接访问 db
控制器<域>.controller.ts取参、调 service、装响应壳SQL、事务、吞异常
服务<域>.service.ts业务规则、事务边界、跨表编排写 SQL 字符串细节
仓储<域>.repo.ts手写参数化 prepared SQL业务判断、读 req / res

下单事务里的分层结构示意

// 05 routes：只挂路径、套守卫、校验
ordersRouter.use(requireAuth);
ordersRouter.post("/", controller.create);

// 06 controller：取参 → 调 service → 装壳
const order = orderService.create(req.auth.uid, body);
res.status(201).json({ code: 0, message: "ok", data: order });

// 07 service：事务边界只在这里
const created = db.transaction(() => {
  assertDishesOnSaleAndSameShop();      // 在售 + 同店
  const total = sumByDbPrice();          // 价格以库为准，不信前端金额
  return { order, items };
})();

// 08 repo：一律参数化，拼接 SQL 视为违规
db.prepare("INSERT INTO orders (order_no, user_id, shop_id, total_cents, status) VALUES (?, ?, ?, ?, 'paid')")
  .run(orderNo, uid, shopId, totalCents);
  • 要点一次事务写三处：orders、order_items、地址快照。任一步失败整体回滚，不留半张单。
  • 要点幂等：order_no 唯一约束 + 冲突重试上限 3 次，前端按钮同步禁用，双击不会拆成两单。
  • 要点鉴权不查库：中间件只验 JWT 签名与 role，登录端点按所用表（users / admins）签发 role。

  • token + 用户信息 + role
  • localStorage 持久化，刷新不掉登录
  • 401 时 clear()，由拦截器统一处理
  • 守卫组件只读这个 store，不发请求

cartStore stores/cart.ts

  • 单店模型：一个购物车只装一家店的菜
  • 跨店加菜先确认，确认后清空再加入
  • 只存内存，不落库，刷新即空（明确的设计决策）
  • 不信任前端金额，提交只传菜品与数量

06数据模型

三个域九张表。表之间靠外键连起来，订单侧刻意冗余快照字段，让历史订单不随改价改址而变。

用户域 3 张

  • users 学生账号：username 唯一 + password_hash
  • admins 管理员账号：独立表，与 users 完全隔离
  • addresses 收货地址：FK user_id，is_default 全局唯一

商品域 3 张

  • shop_categories 店铺分类，首页筛选用
  • shops 店铺：FK category_id，is_active 软删除
  • dishes 菜品：FK shop_id，dish_group 决定详情页分组

交易域 2 张

  • orders 订单：FK user_id / shop_id，含收货信息快照与状态
  • order_items 明细：逐行结构化，禁止 JSON，含菜名与单价快照

关系连线 1 : N

  • users → addresses、users → orders
  • shop_categories → shops → dishes
  • orders → order_items ← dishes（引用 dish_id）
  • admins 不参与业务外键，仅作权限主体

四个刻意的设计答辩常被追问

  • 快照orders 存收货人/电话/楼栋/房间，order_items 存 dish_name 与 unit_price_cents。管理员改价、用户改地址，历史订单展示不变。
  • 软删店铺与菜品用 is_active，有历史订单的行永不物理删除；下架后用户端不可见，历史订单仍可打开。
  • 金额所有 *_cents 为 INTEGER，避免浮点误差；展示层由 lib/money.ts 统一 ÷100。
  • 索引idx_orders_user(user_id, status, created_at DESC) 支撑「我的订单」按状态倒序；idx_items_dish 为阶段二的近 30 天销量聚合留位。

07订单状态机

四态一次定稿。shared/src/order-status.ts 是前后端唯一事实源，按钮显隐与后端推进都读它。

待接单 配送中 已完成 已取消（终态）

合法迁移表 ORDER_FLOW

paid:       ["delivering", "cancelled"]
delivering: ["completed"]
completed:  []
cancelled:  []

推进入口唯一 transition()

UPDATE orders SET status = :to
WHERE id = :id AND status = :from

影响行数为 0 即说明状态已被并发改变，抛 3001 / 409，不做覆盖写。

详情页时间线五节点，未到达置灰

  • 下单成功created_at
  • 模拟支付完成paid_at
  • 店家接单accepted_at
  • 配送中delivered_at
  • 已送达completed_at

取消单的第 5 个节点替换为「已取消」，取 cancelled_at。节点构造同样集中在 buildOrderTimeline()，页面不自己算。

域之间的依赖谁读谁，谁不改谁

auth      ── 写 users / admins，签发 JWT（role 由所用表决定）
shops     ── 只读商品域，is_active 过滤；搜索同时匹配店名与菜名
orders    ── 读 shops / dishes 校验在售与同店；写 orders / order_items（事务）
addresses ── 读写自己的表；所有语句按 JWT 的 uid 过滤，越权返回 404
admin     ── 维护商品域；订单相关接口物理上复用 orders 模块
             （adminOrdersRouter），由 adminRouter 的 requireAdmin 统一守卫
  • 为什么管理端订单接口放在 orders 模块，是为了让状态机推进只有一份实现；admin 模块只负责「商品维护」与「上传」。
  • 为什么orders 只读商品表而不写，库存与销量改动全部收敛在管理端接口，避免下单链路出现隐式写操作。
  • 为什么每个 service 都按 uid 过滤查询，不靠前端传 userId，越权访问自然变成 404。

09测试与门禁

三层防线：类型与规范在写代码时拦住，集成测试在接口层拦住，端到端在真实浏览器里验收。

层级位置规模覆盖什么命令
类型 + 规范全仓3 个 tsconfig跨包类型一致性、lint 规则npm run typecheck
npm run lint
单元shared/src/*.test.ts2 个文件状态机迁移表、zod schema 边界npm run test
集成server/test/7 个文件 75 例supertest 打接口：鉴权分层、越权、取消限制、seed 幂等、限流npm run test

本地起项目按顺序执行

npm install          # 根目录，一次装齐三个 workspace
npm run seed         # 幂等重建演示数据（清库后重灌）
npm run dev          # 并发起 server:3000 + client:5173
npm run test         # 75 例集成 / 单元
npm run test:e2e     # 14 例端到端（自动 seed + 构建 + 预览，约 1.6 分钟）

E2E 为什么用生产构建

  • dev 模式每个新浏览器上下文要冷拉数百个 ESM 模块，单页约 10s
  • 改为 vite build + vite preview 后单页不到 1s
  • 预览服务同样代理 /api 与 /uploads

验收稳定性

  • workers: 1：共用一份数据库，串行避免互相污染
  • 每次运行前 seed，用例只依赖确定性数据
  • trace 写系统临时目录，避开同步盘写入阻塞

阶段二的接入位不改既有表

  • 评价order_items 已是逐行结构化明细，新增 reviews 表按 order_id / dish_id 关联即可。
  • 推荐idx_items_dish 已为「近 30 天销量」聚合留位，替换 monthly_sales 的 seed 兜底值。
  • 可视化时间字段齐全（created / paid / accepted / delivered / completed / cancelled），趋势图不需要改表。
